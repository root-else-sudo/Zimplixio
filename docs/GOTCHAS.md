# Known Gotchas

Implementation quirks, removed features, and non-obvious constraints. Read this before touching an area you're unfamiliar with.

**Division of labour with `CLAUDE.md`:** that file describes how the project is *put together* — architecture, conventions, what to follow. This file records *traps* — things that will bite you, decisions that look like mistakes but aren't, and features deliberately removed. Where both touch the same subject, `CLAUDE.md` states the rule and this file explains the failure mode behind it.

---

## Static Files & Build

- **STORAGES setting — production uses the NON-manifest backend**: `settings/prod.py` sets `staticfiles` to `whitenoise.storage.CompressedStaticFilesStorage`, not the `Manifest` variant. This is deliberate but was never a design decision — it was swapped in during Railway deploy troubleshooting (commit `6ee21d0`) and kept because it works. Trade-off: without the manifest, filenames are not content-hashed, so WhiteNoise cannot mark assets immutable and falls back to its default `max-age=60`. **That 60 is not what visitors get** — Cloudflare overrides it at the edge, and production actually serves `cache-control: public, max-age=14400`. So the cost is not frequent re-fetching; it is that a file's URL never changes when its bytes do, which is why renaming is the only reliable cache bust (see "Renaming a static asset" under Design System & CSS). Do not "fix" the docs by switching the backend — restoring `CompressedManifestStaticFilesStorage` may break the build, since it fails `collectstatic` with `ValueError: Missing staticfiles manifest entry` if any template or CSS file references a static file that does not exist. If you do restore it, verify `collectstatic` passes first.
- **One React bundle for everything**: `static/dist/framework-accordion.js` (built from `frontend/`) drives both the hub-and-spoke diagram and the assessment wizard. Rebuilding with `cd frontend && npm run build` updates both.
- **No tsParticles / no CDN for hero effect**: The hero animation is pure vanilla JS canvas (ImageData pixel writing). The tsParticles CDN was removed. `cdn.jsdelivr.net` was also removed from the CSP `script-src` directive in `core/middleware.py`.

## Media Storage (Cloudflare R2)

- **Media does not travel between environments**: a showcase image uploaded locally does not exist in production, and vice versa — the two environments write to entirely different backends. `MEDIA_ROOT`/`MEDIA_URL` in `base.py` look authoritative but are unused in prod, since `STORAGES['default']` overrides the backend.
- **Do not re-hardcode the R2 domain in the CSP**: it was hardcoded in `core/middleware.py` until it was made to derive from `settings.AWS_S3_CUSTOM_DOMAIN`. Rotating the bucket while only updating the env var would then have left every image silently blocked, visible as broken images with nothing but a console CSP violation. The helper tolerates the value with or without a scheme and strips a trailing slash, so both `pub-xxx.r2.dev` and `https://pub-xxx.r2.dev/` work.
- **Dev allows no R2 images in CSP**: `AWS_S3_CUSTOM_DOMAIN` is only defined in `prod.py`, so in dev `img-src` is just `'self' data:` — correct, since dev serves media from disk. If you point a local instance at the production bucket, set `AWS_S3_CUSTOM_DOMAIN` locally too or every image will be blocked.
- **R2 env vars have no defaults**: `prod.py` calls `env('R2_ACCESS_KEY_ID')` etc. with no fallback, so a missing variable raises `ImproperlyConfigured` at startup and the app will not boot. Intentional (fail loud), but it means `settings/prod.py` cannot be loaded locally without the full R2 credential set.
- **Nothing cleans up R2 objects**: uploads are never overwritten (`AWS_S3_FILE_OVERWRITE = False` suffixes same-name files) and deleting a `ShowcaseScreenshot` row does not delete the object in the bucket. Orphans accumulate silently.
- **Media is world-readable**: `public-read` ACL with unsigned, unexpiring URLs. Do not put anything non-public behind these fields.

## Database & Performance

- **`CONN_MAX_AGE` must stay set — it is worth ~800ms per request**: `settings/base.py` sets `CONN_MAX_AGE` (default 600, overridable via env) and `CONN_HEALTH_CHECKS = True`. Django's default of `0` opens and tears down a PostgreSQL connection on *every* request. Before this was set, any request touching the database cost ~800ms more than one that did not — identically for JSON endpoints and template renders, so it was clearly connection setup rather than query time. Do not remove these lines or "simplify" them away.
- **The Railway web service and Postgres service must be in the same region**: they were originally split (web in US East / Virginia, Postgres in EU West), so every query crossed the Atlantic at ~85ms per round trip. Page cost scaled with query count — visible as `/contact/` ~192ms vs `/showcase/` ~370ms of database overhead. Moving Postgres to the web service's region removed it entirely. If page loads ever regress site-wide, check region alignment first.
- **Measured impact of the two fixes together** (median, warm connection, `/showcase/` → `/contact/` range): originally 793–1074ms per page → 258–436ms after `CONN_MAX_AGE` → **60–115ms after region alignment**, a 10–16× improvement. Database-attributable overhead is now within measurement noise (−11ms to +44ms against a ~71ms no-DB baseline).
- **How to re-measure**: compare an endpoint that touches the DB against one that does not. `/book/slots/` with no `date` param returns `400` before reaching the ORM, and `/static/css/main.css` is served by WhiteNoise without a Django view — either works as a no-DB baseline. `/book/slots/?date=<future>` runs real queries with no template, which separates database cost from template rendering.
- **`site_context` re-queries `NPSMetric` on every template render**: in `core/context_processors.py`, `cache.set(NPS_CACHE_KEY, active, …)` stores `None` when no active metric exists, and a cached `None` is indistinguishable from a cache miss — so the query runs every time. Harmless now that the database is same-region (~2ms), but it is why *every* page hit the database during the latency investigation. Fix by caching a sentinel if it ever matters again.

## Templates & Django

- **`TIME_ZONE` is `America/New_York`, not UTC — and that is a display setting, not a storage one**: `USE_TZ = True`, so aware datetimes are still stored in UTC; `TIME_ZONE` only controls rendering and how datetime form input is read. It was `'UTC'` until 17 Nov 2026, which made the admin show `created_at`/`submitted_at` five hours ahead — and in the booking changelist that sat directly beside `requested_date`/`requested_time`, which are **naive** fields already holding Eastern values. One table row, two timezones, nothing marking which was which. Changing `TIME_ZONE` does **not** shift naive `TimeField`/`DateField` values (guarded by `AdminTimestampDisplayTests`), and does not affect `today_in_booking_tz()`, which converts explicitly. Keep it in sync with `BOOKING_TIMEZONE`; they are deliberately separate settings because one is rendering and the other is a business rule.
- **`{% load static %}` in partials**: `_header.html` includes its own `{% load static %}` at the top — required because partials do not inherit the parent template's loaded tags.
- **Hero particle effect — `#hero-particles` div required**: `particles-hero.js` looks for `<div id="hero-particles">` inside the hero `<section>`, styled `position:absolute; inset:0; z-index:1; pointer-events:none` in `main.css`. Ten templates carry it, including `404.html`. The script listens for mousemove on `document` rather than the canvas, precisely because the canvas has `pointer-events:none` — moving that listener onto the canvas silently kills the parallax.
- **HomePageView cross-app query**: `HomePageView` imports `showcase.ShowcaseProject` to fetch `featured_projects` for the homepage — changes to the showcase model can affect the homepage.
- **Stray characters in project-specific templates**: When editing `detail-simple-forecast.html` or `detail.html` manually, watch for stray characters outside `{% block %}` tags — they will be silently rendered into the page.

## Showcase Detail Templates

- **Gallery thumbnails**: Use `object-contain` (not `object-cover`) so icon-style images display fully without cropping.
- **Cross-origin iframe CSRF**: Embedded apps (e.g., recomares.com) that use POST-based actions (like Django `set_language`) will fail in the iframe due to third-party cookie blocking. The "Open in new tab" fallback link is provided.
- **Iframe-embedded showcase apps must allow framing**: Any external app added to the showcase with `live_demo_url` must not send `X-Frame-Options: SAMEORIGIN`. Remove `XFrameOptionsMiddleware` from the embedded app's `MIDDLEWARE` setting to allow cross-origin embedding.
- **Showcase carousel only loops when a card is off-screen**: `showcase-carousel-v2.js` clones the first/last N slides (N = 3 desktop, 2 tablet, 1 mobile) *only* when there are more projects than fit. At N or fewer it skips cloning entirely, adds `.showcase-carousel-static` (centres the row, fixes cards at 380px, hides the arrows) and leaves the track untransformed — otherwise sliding just rotates duplicates through the visible slots, and a single filtered result cycles the same card forever. **With 3 published projects this means the homepage "Featured Solutions" and the unfiltered gallery are both static on desktop**; the carousel returns at 4 projects. Both layouts are re-evaluated on resize, since the same count can be static on desktop and a real carousel on mobile.
- **Showcase carousel auto-play pauses on hover/focus**: Stays paused if the user tabs in and doesn't tab out — intentional for accessibility.

## Design System & CSS

- **Color palette — Tailwind `indigo` remapped**: The `indigo` color scale in `base.html` Tailwind config is overridden to a navy/electric-blue palette (`indigo-600 = #2563eb`, `indigo-800 = #0f2044`, `indigo-900 = #0a1628`). Do not add raw hex values for blue; use `indigo-*` classes.
- **Logo SVG sizing**: `static/images/logo.svg` has no fixed `width`/`height` attributes (removed so CSS controls size). The viewBox is cropped to the content area (`278 337 1656 426`).
- **HPE logo is `HPE-v2.svg`, not `HPE.svg`**: The text paths originally used `fill:#ffffff`, which was invisible on the light homepage background. They are now `fill:#1f2937` (the green icon element, `fill:#00b188`, was never changed). The file was **renamed** as part of that fix because static assets carry no content hash — see "Renaming a static asset is the only cache bust" below.
- **Renaming a static asset is the only reliable cache bust**: WhiteNoise runs `CompressedStaticFilesStorage` (non-manifest), so a static file's URL never changes when its bytes do. Cloudflare then serves it with `cache-control: public, max-age=14400`. Chrome revalidates on a hard refresh, but **Safari does not** — it keeps decoded `<img>` SVGs in a per-process memory cache above the network layer, which the Web Inspector's "Disable Caches" checkbox does not clear. A visitor who loaded the old bytes keeps them indefinitely. When you change a static asset's *appearance*, rename the file and update its `{% static %}` references; editing in place is not enough.
- **Credential logo sizing is per-file**: PayPal/IBM/HPE use `.credential-logo-xl` (280×104px) and Intel uses `.credential-logo` (140×52px) because the SVGs have different native aspect ratios.
- **`.logo-magnetic` on multiple elements**: Applied to the logo `<a>` and desktop "Book a Call" button in `_header.html`. Do not apply to the mobile "Book a Call" (inside the dropdown menu).
- **PDCA section — no GSAP, no JS file**: Pure CSS + AOS only. Do not add JS animation libraries — `cdnjs.cloudflare.com` is not in the CSP `script-src` allowlist.
- **PDCA description reveal is hover-only on desktop**: `.pdca-desc` uses `max-height: 0` → `max-height: 200px` on `:hover`. On mobile (≤767px), descriptions are always visible via CSS override.
- **Do not add ambient blur circles to a `.hero-animated-bg` section — they read as grey discs, not ambience**: the `<div class="absolute inset-0 opacity-10">` wrapper with `bg-white` / `bg-indigo-400 rounded-full blur-3xl` children was designed in `0d99286` for the *static* `bg-gradient-to-br from-indigo-700 via-indigo-800 to-gray-900` hero. `4fab50c` replaced that background with `.hero-animated-bg` and added the particle canvas, but left the circles in place. A 10%-opacity white overlay adds a near-constant **+23 RGB** regardless of what is beneath it; against the animated gradient's `#060c18` stop — `rgb(8,16,33)`, nearly black — that is a ~4× relative lift, so the circle stops being ambience and becomes a visible object. Worse, `heroGradientShift` *pans* the gradient, so the near-black stop sweeps under the circles and they fade in and out on a 14-second loop, which reads as a bug in the particle animation rather than a static background element. All 12 of these were removed; the hero's depth now comes from the gradient animation plus `particles-hero.js`. The three circles that remain — `privacy_policy.html`, `cookie_policy.html`, and `detail-framework.html`'s `#assessment-cta` — sit on the lighter *static* gradient where the effect still works, and should be left alone.

## Booking

- **`requested_date`/`requested_time` are hidden inputs**: Populated by JS before form submission. If JS is disabled the form cannot be submitted — this is by design.
- **Never use `date.today()` to decide whether a date is still bookable — use `today_in_booking_tz()`**: production runs UTC with no `TZ` set, while availability is published in `BOOKING_TIMEZONE` (`America/New_York`). `date.today()` therefore rolls over at 19:00 Eastern, and `available_days_view` / `available_slots_view` both skip `d <= today` — so from 7pm every weeknight the **entire next day** vanished from the calendar, all twelve 10:00–16:00 slots, not just evening ones. Fixed 17 Nov 2026. The trap for anyone testing this: a developer machine in Eastern makes `date.today()` coincidentally correct, so the bug is invisible locally and only appears on the UTC server. `BookingDateBoundaryTests` therefore patches **both** `django.utils.timezone.now` *and* `booking.views.date` — the first drives the fix, the second reproduces what a UTC server returns. Patching only the first gives a green test over a live bug.
- **Zoom call link is env-driven, not hardcoded**: `booking_visitor_confirmed.html` renders `{{ zoom_url }}`, injected by `BookingEmailService.send_visitor_confirmed()` from `settings.ZOOM_MEETING_URL` (`settings/base.py`). To change the meeting link, update the `ZOOM_MEETING_URL` env var — do not edit the template. The setting defaults to `''`, so if the env var is missing the email still sends with an empty `href` and a dead "Join Zoom Meeting" button, with no error raised.
- **The calendar invite's `DTSTART` must be converted from Eastern, never combined naively**: `requested_date` and `requested_time` are naive values that *mean* Eastern, but `DTSTART` is a UTC instant. `booking/calendar_invite.py` combines them with `booking_tz()` attached and only then converts. A naive `datetime.combine()` produces an invite five hours off, and — unlike the availability bug above — it fails silently in both directions: the email shows the right time while the calendar entry is wrong. `CalendarInviteTests` covers both a winter and a summer date, because a hardcoded `-5` offset passes the EST case and breaks every EDT booking.
- **The invite is attached twice on purpose**: once as an alternative part (`text/calendar; method=REQUEST`) and once as an `invite.ics` attachment. Clients disagree about which they honour — dropping either loses Accept/Decline buttons for one group. Verified by the MIME structure, not by eye: `multipart/mixed` → `multipart/alternative` (plain, html, calendar) + attachment.
- **A cancelled booking must send `METHOD:CANCEL` with a higher `SEQUENCE`**: same UID, `SEQUENCE:1`. Without the bump, clients treat it as a duplicate of the original request and the dead meeting stays on the visitor's calendar. `UID` is derived as `booking-{pk}@zimplixio.com` — changing `UID_DOMAIN` orphans every invite already accepted.
- **Every prospect gets the same Zoom link**: `ZOOM_MEETING_URL` is one static Personal Meeting Room, not a per-meeting link, because per-meeting links need the Zoom API. Two consequences accepted knowingly (18 Nov 2026): back-to-back calls share a room, and once the link is in a calendar event it persists indefinitely rather than being archived with an email. Mitigated by Zoom's waiting room, not by code.

## Public Form Anti-Spam

Lives in `core/antispam.py` and is used by **both** the contact form (`pages/forms.py`) and the booking form (`booking/forms.py`). Submissions are gated on a decoy field plus a signed render timestamp (`ts`), and the two signals are treated **asymmetrically on purpose**:

- **Only `too_fast` is refused; every other reason is flagged and stored**: a POST arriving under `MIN_DWELL_SECONDS` (3s) raises a `ValidationError` and never becomes a row. `honeypot`, `no_token` and `stale_token` still save the submission with `is_spam=True` instead. The asymmetry is deliberate: no human fills this form in under three seconds, but browser autofill can populate the decoy and a missing or day-old token can just mean a tab left open overnight. Those stay recoverable; the sub-3-second POST does not need to be.
- **The ORDER of checks in `_spam_reason()` is load-bearing**: only the first signal found is returned, and that decides refuse-vs-store. Conclusive signals must be checked first. The dwell floor was originally checked *after* the decoy, which meant a submission tripping both was stored rather than refused — one line in the bot's script would have refilled the table. Never reorder these checks so that a `_REFUSED_REASONS` member sits below a flag-only one.
- **`clean()` runs even after field validation has already failed**, so a flagged submission with an invalid field is logged and then silently discarded — it never reaches `form_valid()` and never becomes a row. This is why the log distinguishes `discarded (reason; invalid: field)` from `flagged as spam (reason)`. Since refused and discarded submissions leave nothing in the database, the log is the only record that they happened; keep the two wordings distinct.
- **A refused visitor can simply press Send again, and that is load-bearing**: the re-rendered bound form echoes the *original* `ts` value back from `self.data`, so by the time they retry, the token has aged past the 3-second floor and the submission succeeds. Do **not** "fix" the invalid-POST path by stamping a fresh token — that would reset the clock on every attempt and make the rejection permanent for a genuine false positive.
- **The rejection message is deliberately uninformative**: `REJECTION_MESSAGE` says nothing about timing. A bot author reading the response must not learn which signal to tune. `ContactTooFastRejectionTests.test_the_error_does_not_reveal_the_timing_rule` enforces this — do not make the copy more helpful.
- **A flagged (not refused) submission is silent and unrecoverable for the visitor**: `ContactView.form_valid()` skips the confirmation email when `is_spam` is set, so a false positive there sits in the admin with the visitor never told. This is the whole reason `too_fast` refuses rather than flags.
- **The booking form was unprotected until 17 Nov 2026**, and it is the more dangerous of the two: `/book/` is linked from the header of every page, and each submission sent **two** emails — an acknowledgement to whatever address was typed in, plus an admin notice. That is the same shape as the contact form before the campaign that got `team@zimplixio.com` restricted. It had never been found by bots; this was exposure, not damage. Each form carries its own `TOKEN_SALT`, so a token harvested from one cannot be replayed against the other (verified).
- **Two different bots hit this form, and each is caught by a different signal**: measured 13–16 Nov 2026 over 768 submissions. The high-volume one (name `Robertfus`, ~10–15/hour) fetches `/contact/`, parses the signed token, echoes it back, and ignores fields it does not recognise — so it trips `too_fast` and never the decoy. A second, low-volume one (~5/day, 8–12-character lowercase gibberish in both name and company) fills *every* field including the decoy but takes longer than 3 seconds — so the honeypot is the only thing that catches it. **Do not remove either signal on the grounds that one looks idle**; each is load-bearing against a different operator, and which one appears idle changes month to month.
- **Cloudflare Bot Fight Mode does not help here**: measured against the `Robertfus` campaign and caught **0%** — ~41 submissions/hour both before and after enabling it, with the traffic never appearing in Security Events. It was turned back off. Reach for the application filter, not the edge toggle. A Managed Challenge on `GET /contact/` was considered and rejected: it would put an interstitial on the primary conversion path to stop traffic Django already stops for free.
- **`/contact/` must never be edge-cached**: the dwell token is stamped into the HTML at render time. A cached page would hand every visitor the same `ts`, which goes `stale_token` for everyone after 24h. Cloudflare currently reports `cf-cache-status: DYNAMIC` for it — keep it that way.

## Outbound Email & Deliverability

All transactional mail sends from `team@zimplixio.com` through `smtp.office365.com` (basic auth, STARTTLS on 587). DNS for `zimplixio.com` is hosted at **Cloudflare** (`quentin.ns` / `megan.ns.cloudflare.com`), not at GoDaddy — `include:secureserver.net` in the SPF record is a reference to GoDaddy's sending IPs, not a sign of who hosts the zone.

- **SPF and DKIM were both broken from the Microsoft 365 migration until 16 Nov 2026**: SPF read `v=spf1 include:secureserver.net -all`, which authorises GoDaddy and hard-fails everything else — including Microsoft, where the mail actually originates. No DKIM selectors existed. With DMARC at `p=quarantine`, receiving servers were being explicitly instructed to junk every message. Fixed by adding `include:spf.protection.outlook.com` and publishing the two DKIM CNAMEs. Verified end to end: `dkim=pass header.i=@zimplixio.com header.s=selector1`, `spf=pass`, `dmarc=pass (p=QUARANTINE dis=NONE)`.
- **⚠️ Never enable MFA on `team@zimplixio.com`**: it is a service account the Django app authenticates as with a username and password. Enforcing MFA breaks basic auth and silently stops *every* outbound email — contact acknowledgements, all four booking emails, assessment lead alerts. Microsoft's unblock and security wizards actively recommend enabling it; decline. Moving to OAuth2/Graph is the prerequisite for ever turning it on.
- **If the mailbox password is ever reset, update `EMAIL_HOST_PASSWORD` in Railway in the same sitting**: `ContactEmailService.send_visitor_received()` and the `BookingEmailService` methods catch `Exception` and route it to `logger.exception`, so an auth failure produces a log line nobody is watching and no other symptom. The site keeps accepting submissions and quietly replies to nobody.
- **Mail-related CNAMEs in Cloudflare must be "DNS only" (grey cloud)**: a proxied record returns Cloudflare's own IPs instead of the target, which breaks the lookup entirely and reports nothing useful at either end. This already bit `autodiscover`, `sip`, `lyncdiscover`, `msoid` and `email`, which are all still proxied and should be flipped — `autodiscover` being the one that matters, since it breaks Outlook and mobile client setup. The `_domainkey` selectors are correct. Web records (root, `www`, `crm` → Railway) *should* stay proxied.
- **Microsoft restricted this mailbox once, on 9 Nov 2026**, after bot-driven contact submissions generated ~1,873 acknowledgement emails to scraped third-party addresses in eight days. From Microsoft's side that is indistinguishable from a compromised mailbox. Symptom: SMTP `AUTH`, `MAIL FROM` and `RCPT TO` all still return `250`, so probing short of `DATA` looks healthy — the restriction only shows on the **Restricted entities** page (`security.microsoft.com/restrictedentities`) and in the alert email. Unblocking takes up to an hour to propagate. The root cause is fixed by the contact form spam filter; if it ever recurs, suspect the filter before suspecting a real compromise.
- **Domain reputation recovers slowly.** Authentication being correct stops the self-inflicted quarantining immediately, but the reputation damage from those 1,873 messages fades over days of clean sending. Occasional junk-foldering in the weeks after 16 Nov 2026 is residue, not regression.
- **DMARC `rua` points at `dmarc_rua@onsecureserver.net`** — a GoDaddy default. Aggregate reports have never reached anyone here. Pointing it at a monitored address would have surfaced the SPF/DKIM failure months earlier.

## Cloudflare Edge

The site is proxied through Cloudflare in front of Railway (`server: cloudflare`, `cf-ray`, `cf-cache-status` in every response). Almost everything passes through untouched, with one exception:

- **Production `/robots.txt` does not match the repo — this is expected, not a stale deploy**: Cloudflare's managed robots.txt / AI Crawl Control feature *prepends* a large block to the response after Django has rendered it: a Content Signals Policy preamble declaring `Content-Signal: search=yes,ai-train=no,use=reference` (verified still current 16 Nov 2026), followed by a `Disallow: /` group per blocked crawler. The repo's own two rules survive verbatim at the bottom. **Do not trust a crawler count written down here — Cloudflare grows this list.** It was ~50 lines and 9 crawlers when first documented; by 16 Nov 2026 it was ~130 lines and 32. Check the current state with `curl -s https://zimplixio.com/robots.txt`, never by reading this file. Nothing in the codebase produces or is overridden by that block — to change it, use the Cloudflare dashboard, not `templates/robots.txt`.
- **Only robots.txt is modified**: verified — HTML pages contain no Cloudflare-injected scripts and no `/cdn-cgi/` references, and `sitemap.xml` is pure Django output. Do not assume other production/repo differences have the same explanation.
- **The merged file has two `User-agent: *` groups**: Cloudflare's (`Allow: /`) and the repo's (`Disallow: /zm-admin/`). RFC 9309 requires compliant crawlers to merge duplicate groups and Google does, but a crawler that honours only the first match would ignore the admin rule. Low impact — the admin is behind authentication, and `robots.txt` is a crawling hint, not access control.
- **This is a Cloudflare default, it is no longer AI-only, and nobody here chose it**: as of 16 Nov 2026 the blocked list includes ordinary search and SEO crawlers alongside the AI ones — **`Baiduspider`** (Baidu search), **`PetalBot`** (Huawei search), `GoogleOther`, `SemrushBot-SWA`, `Diffbot`, `atlassian-bot`. So the setting costs more than staying out of AI training data: it also costs discoverability on those engines, and keeps the site out of AI-assistant answers. Review it deliberately in the Cloudflare dashboard rather than inheriting whatever Cloudflare adds next.
